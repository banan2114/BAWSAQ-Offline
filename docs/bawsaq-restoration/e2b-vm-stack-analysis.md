# E2b — Аудит стека RAGE Script VM и безопасный дизайн обхода ворот BAWSAQ

**Статус:** Этап E2b (статический анализ и проектирование; файлы `game-scripts/*.ysc` не модифицированы, бинарные патчи не изготавливались, в памяти/рантайме игры изменения не выполнялись).  
**Объект анализа:** активная пара скриптов GTA V Enhanced `2.0.1158.16` — `game-scripts/appinternet1.ysc` и `game-scripts/stock_controller1.ysc` (идентифицированы в [E2a](e2a-script-resolution.md), формат `v2` 131 опкод).

Во всех разделах ниже строго разделены:
- **Подтверждённые факты** (проверенные байты/адреса в YSC и точные реализации VM),

- **Гипотезы** (ожидаемое поведение в игре при первом эксперименте C1),

## 1. Подтверждённая семантика инструкций RAGE Script VM

Семантика опкодов установлена **не по их мнемоникам**, а сведена по **четырём независимым реализациям/спецификациям GTA V RAGE Script VM** (включая GEN9/Enhanced):

1. `alexguirre/rage-sc-tools` (`docs/InstructionSet.md`) — спецификация стековых переходов `0x00..0x7E`.
2. `calamity-inc/Stand-OSS` (`Stand/script_vm_reimpl.cpp`) — C++-реимплементация `rage::scrThread::Run`.
3. `ShinyWasabi/scrDbg` (`src/lib/rage/gta5/scrThread.cpp`) — отладочная реимплементация `RunThreadInternal` для `GEN8` и `GEN9`.
4. `Vali0004/Ovr` (`Ovr/src/hooking/hooks/script_vm.cpp`) — независимая C++-реимплементация цикла `rage::scrThread`.
5. Дополнительно сверены размеры операндов и коды `ENTER=45`/`LEAVE=46` в `Parik27/V.Rainbomizer` (`lib/scrThread.cc`).

Во всех четырёх источниках индекс `sp` указывает на **текущую вершину стека (`sp[0]`)**, стек растёт вверх (`++sp` при push, `--sp` при pop), `fp` указывает на базу кадра текущего вызова (`fp[0..p-1]` — аргументы).

### 1.1. Механика стека и фреймов (`CALL`, `ENTER`, `LEAVE`)

| Опкод (`v2` hex) | Точная C++-семантика (`Stand-OSS` / `scrDbg` / `Ovr`) | Эффект на `sp`, `fp`, `pc` |
|---|---|---|
| `CALL` (`0x5D`) `imm24` | `++sp; sp[0].Uns = next_pc; SET_PC(imm24);` | `+1` слово на стеке (кладёт адрес возврата поверх `p` аргументов, заранее положенных вызывающим кодом) |
| `ENTER` (`0x2D`) `p, v, nlen` | `(++sp)->Int = fp - stack; fp = sp - p - 1; while (v--) (++sp)->Any = 0; sp -= p;` (плюс пропуск `nlen` байт имени) | Формирует кадр: `fp[0..p-1]` = аргументы, `fp[p]` = `returnAddr`, `fp[p+1]` = `callerFP`, `fp[p+2 .. p+1+v-p]` = нулевые локалы. После `ENTER` глубина операндного стека относительно базы тела функции = **`0`** |
| `LEAVE` (`0x2E`) `p, r` | `ret = sp - r; sp = fp + p - 1; fp = stack + sp[2].Uns; newPc = sp[1].Uns; SET_PC(newPc); sp -= p; while (r--) *++sp = *++ret;` | Сбрасывает `sp` **абсолютно относительно `fp`** (`fp + p - 1`), читает `returnAddr = fp[p]` и `callerFP = fp[p+1]` **от `fp`, а не от текущего `sp`**, снимает `p` аргументов и переносит `r` возвращаемых значений с `(old_sp - r + 1 .. old_sp)` на новую вершину стека |

**Ключевой доказанный вывод о `LEAVE(2, 0)` (`2e 02 00`) в `func_9474`:**
- Поскольку `LEAVE` читает `returnAddr` и `callerFP` через `fp` (`fp[2]` и `fp[3]`), а при `rcount == 0` цикл копирования `while (r--)` выполняется 0 раз, лишний операнд, оставленный на стеке к моменту `LEAVE`, **не портит адрес возврата при самом `LEAVE`** — он отбрасывается сбросом `sp = fp + p - 1`.
- **Однако** до достижения `LEAVE` этот лишний операнд остаётся на стеке во всех промежуточных базовых блоках и сдвигает `sp` на `+1` для всей остальной части функции (см. анализ Варианта A в §4).

### 1.2. Опкоды ворот и кандидатных патчей

| Опкод (`v2` hex) | Длина | Семантика в `scrThread` | Дельта глубины стека |
|---|---:|---|---:|
| `NOP` (`0x00`) | 1 B | `JUMP(code - base);` (холостой шаг, без изменения стека) | `0` |
| `INOT` (`0x06`) | 1 B | `sp[0].Int = (sp[0].Int == 0);` | `0` (`-1 + 1`) |
| `IOR` (`0x20`) | 1 B | `--sp; sp[0].Int |= sp[1].Int;` | `-1` (`-2 + 1`) |
| `IAND` (`0x1F`) | 1 B | `--sp; sp[0].Int &= sp[1].Int;` | `-1` (`-2 + 1`) |
| `DUP` (`0x2A`) | 1 B | `++sp; sp[0].Any = sp[-1].Any;` | `+1` (`-1 + 2`) |
| `DROP` (`0x2B`) | 1 B | `--sp;` | `-1` |
| `NATIVE` (`0x2C`) `ar, hi, lo` | 4 B | Вызов натива (`argCount = (ar>>2)&0x3F`, `retCount = ar&3`), затем `sp -= argCount - retCount;` | `retCount - argCount` (для `NETWORK_IS_SIGNED_ONLINE`: `0 -> +1`) |
| `GLOBAL_U16_LOAD` (`0x53`) `u16` | 3 B | `++sp; sp[0].Any = globals[0][u16].Any;` | `+1` |
| `GLOBAL_U24_LOAD` (`0x62`) `u24` | 4 B | `++sp; sp[0].Any = globals[0][u24].Any;` | `+1` |
| `J` (`0x55`) `s16` | 3 B | `JUMP(next_pc + s16);` | `0` |
| `JZ` (`0x56`) `s16` | 3 B | `--sp; if (sp[1].Int == 0) JUMP(next_pc + s16);` | **`-1`** |
| `INE_JZ` (`0x58`) `s16` | 3 B | `sp -= 2; if (!(sp[1].Int != sp[2].Int)) JUMP(next_pc + s16);` | `-2` |
| `ILT_JZ` (`0x5B`) `s16` | 3 B | `sp -= 2; if (!(sp[1].Int < sp[2].Int)) JUMP(next_pc + s16);` | `-2` |
| `SWITCH` (`0x65`) | `2 + 6*N` | Pops `sp[0]` (`--sp`) и сравнивает с таблицей `(case, target)` | `-1` |
| `PUSH_CONST_0` (`0x71`) | 1 B | `++sp; sp[0].Int = 0;` | `+1` |
| `PUSH_CONST_1` (`0x72`) | 1 B | `++sp; sp[0].Int = 1;` | `+1` |

## 2. Полная реконструкция потока управления (CFG) `appinternet1::func_9474`

### 2.1. Входящие вызовы и внешние переходы

- Функция `func_9474` (`0x2FC392..0x2FCCD3`, `pcount=2`, `vcount=12`, `rcount=0`, **882 инструкции**) имеет ровно **2 входящие точки вызова**, обе из `appinternet1::func_9394`:
  1. `func_9394 @ 0x2EF34E`: перед вызовом выставляет `Global_77568 = 1` (`0x2EF346`, режим **BAWSAQ**) и передаёт `(local_param0, local_param1)`.
  2. `func_9394 @ 0x2EF39F`: перед вызовом выставляет `Global_77568 = 0` (`0x2EF397`, режим **LCN**) и передаёт `(local_param0, local_param1)`.
- Полный обход всех 9 777 функций `appinternet1.ysc` подтвердил: **0 внешних `J`/`JZ`/`SWITCH`/`CALL`-переходов** во внутренние адреса `0x2FC393..0x2FCCD5`.

### 2.2. Пошаговая структура CFG (вход, ворота, ветки, выходы)

1. **Пролог (`BB00`: `0x2FC392..0x2FC3A4`):** обнуляет три локальные переменные (`fp[5..7] = 0`), проверяет `iParam1 != 15` (`INE_JZ -> 0x2FC432`). При `iParam1 == 15` сразу перепрыгивает в `BB22` (`0x2FC432`), минуя все гейты.
2. **Проверка заполненного портфеля (`BB01..BB05`: `0x2FC3A7..0x2FC3CE`):** если `Global_65068 != 0`, в зависимости от `Global_77568` вызывает `func_9733` (`0x315922`) со строкой `WWW_BAWSAQ_COM_S_ERROR` или `WWW_LCN_D_EXCHANGE_COM_S_ERROR`, записывает `Global_77542 = -1` и завершается через **`LEAVE@0x2FC3CE` (`BB05`)**.
3. **Разделение BAWSAQ / LCN (`BB06`: `0x2FC3D1..0x2FC3D5`):**
   - `Global_77568 == 0` (LCN) → `JZ -> 0x2FC416` (`BB18..BB21`), где проверяется только `Global_80362 || Global_65064`. При провале вызывается `func_9733("WWW_LCN_D_EXCHANGE_COM_S_ERROR")` и **`LEAVE@0x2FC42F` (`BB21`)**; при успехе `JZ -> 0x2FC432` (`BB22`).

4. **Ворота BAWSAQ (`BB07..BB13`: `0x2FC3D8..0x2FC3F9`):** short-circuit-выражение со стековым аккумулятором:
   - `BB07` (`0x2FC3D8..0x2FC3DF`): стек `[]` → `NATIVE NETWORK_IS_SIGNED_ONLINE` → `INOT` (`c0 = !online`) → `DUP` → `INOT` → `JZ -> BB09 (0x2FC3E7)` (стек перед `JZ`: `[c0, !c0]`, после `JZ`: `[c0]`).

5. **Ветка ошибки BAWSAQ (`BB14..BB16`: `0x2FC3FC..0x2FC410`):**

## 4. Сравнение вариантов минимального локального обхода в `func_9474`

Все адреса относятся к **`appinternet1.ysc`**, страница кода **`191` (`0xBF`, размер страницы `0x4000`)**. Уникальная 36-байтовая сигнатура `0x2FC3D8..0x2FC3FC` встречается в файле ровно **1 раз**:

1. **Идеальная стековая эквивалентность (`0`-дельта):** на `0x2FC3D8` натив `NETWORK_IS_SIGNED_ONLINE` (`0 -> +1`) заменяется на `PUSH_CONST_1; NOP; NOP; NOP` (`0 -> +1`), а на `0x2FC3F5` `GLOBAL_U16_LOAD Global_65065` (`0 -> +1`) заменяется на `PUSH_CONST_0; NOP; NOP` (`0 -> +1`). Глубина стека, `fp`, смещения всех инструкций и всех `J`/`JZ`/`SWITCH` остаются **побайтово тождественными оригиналу** на всех 887 инструкциях.
2. **Сохранение `Global_65064` и `Global_80362`:** если `stock_controller1` ещё инициализирует каталог (`Global_65064 != 0`) или внешний скрипт выставил `Global_80362 != 0`, ворота по-прежнему срабатывают штатно (`c1 != 0` или `c2 != 0`).
3. **Изоляция LCN и прочих страниц:**

   - `Global_65068` (переполнение портфеля) проверяется на `0x2FC3A7` **до** гейта.
4. **Невосприимчивость к повторной установке `Global_65065 = 1`:** не требует патча `func_9764` или `stock_controller1::func_4` и не подвержен гонке между записью `Global_65065 = 1` в `appinternet1::func_0` и чтением в `func_9474` в том же кадре.

1. Точная механика `CALL`/`ENTER`/`LEAVE`/`JZ`/`J`/`NOP`/`INOT`/`IOR`/`DUP`/`NATIVE` в RAGE Script VM (`Stand-OSS`, `scrDbg` GEN8/GEN9, `Ovr`, `rage-sc-tools`).
